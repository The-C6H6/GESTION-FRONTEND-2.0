- The application composes HTTP adapters for authentication, user registration, enrolled-student lookup, failed-subject lookup, and ruling creation/search/update/delete with `RealPdfGenerator` and `LocalPdfDocumentStore` for local output. Authentication has no demo fallback.
- Runtime API settings load `API_BASE_URL` (or legacy `IP_ADDRESS`), `RUTA_LOGIN`, `RUTA_AUTENTICACION`, `RUTA_REFRESH`, `RUTA_NUEVO_USUARIO`, `RUTA_VISUALIZAR_INSCRITOS`, `RUTA_REPROBADOS`, `RUTA_GENERAR_DICTAMEN`, `RUTA_LECTURA_DICTAMINACIONES`, `RUTA_MODIFICAR_DICTAMEN`, and `RUTA_ELIMINAR` through python-dotenv. Unit tests inject settings and never require `.env` or the backend.
- Login is `POST /api/auth/login` followed by authenticated `GET /api/auth/me`. The complete active identity and administrator role come only from `/auth/me`; the frontend never decodes JWTs or derives a role from a username.
- Access token, refresh token, and authenticated user live only in one ephemeral `AuthSessionStore` session and are omitted from representations and logs. An authenticated request's first `401` performs one single-flight refresh and one exact replay. Terminal refresh/replay failures clear the complete session, transient refresh errors preserve an established session, and an obsolete concurrent operation cannot replay with or clear a replacement session.
- Controller guards plus role-aware routes, navigation, views, and handlers protect registration and ruling mutations. Normal users retain enrolled-student, failed-subject, candidate, and ruling queries without mutation controls; backend `403` remains authoritative and preserves the session.
- User registration uses an authenticated `POST` to the configured `RUTA_NUEVO_USUARIO` with exactly `username`, `password`, and `is_admin`, expects `201`, and strictly validates the returned created-user identity. Only the confirmed duplicate-username `400` detail receives a specific message.
- The registration form shares the retained request gate used by ruling workflows: one concurrent submission is allowed, the submit action exposes loading, failures preserve form values, and success clears only password and confirmation. Neither production nor test repositories retain the submitted password.
- `UserController` enforces the backend's six-character password minimum before repository access so the UI can explain the failure without issuing a request.
- `ApiInscritoRepository` uses `GET /api/inscritos/{boleta}` and maps the complete API response to `Inscrito`. Both enrolled-student screens show a loading state and reuse the logged-in Bearer token.
- `ApiReprobadoRepository` uses `GET /api/reprobados?boleta=<boleta>`, validates the complete paginated payload and transport item contract, rejects partial pages plus inconsistent student identities, and maps only the identity and subject fields needed by the domain. An empty API page is valid and the selected flow presents it as not found.
- The selected student type determines the lookup source. `Alumno inscrito` uses only `GET /api/inscritos/{boleta}`; `Alumno reprobado` uses only `GET /api/reprobados?boleta=<boleta>`. There is no fallback or mandatory dependency between endpoints: a failed student need not be enrolled and vice versa.
- Failed-subject responses provide the minimal `AlumnoDictaminable` identity used by the ruling flow, then the existing eligibility rule is applied. The memoized request gate prevents duplicate concurrent searches.
- API warning logs intentionally omit request paths and parameters because they can contain the student's boleta. Tokens and response payloads are also excluded.
- Ruling search uses `GET /api/dictaminaciones` with exactly one committed filter (`boleta` or integer `anio`) plus `skip` and `limit=100`. Server pages replace rather than accumulate UI rows; navigation errors preserve the last successful page, while both known no-result `400` details map only in this repository to a neutral empty page.
- The ruling-search request gate blocks concurrent searches and disables filter, query, pagination, and visible row actions while loading. A new search always requests page 1; page navigation keeps the committed filter and shows the server total and visible range.
- Ruling update uses `PUT /api/dictaminaciones/{clave}` with exactly `{"Dictaminacion": "..."}` and permits only the centralized one-refresh/one-replay authentication recovery. The selected `Dictamen` is the source of truth: clave, boleta, alumno, fecha, and year are read-only and the controller rejects a response that changes them.
- Update is integrated into the paginated search view. Exactly one checked row is required; save, search, delete, picker, generation, and local PDF persistence share one request gate. The administrator update editor captures dictaminación, director, and session date; desktop destination selection and path validation happen before the single `PUT`; the final backend row replaces only that row before PDF generation; unchanged dictaminación is a neutral no-op before selector or output; cancellation, blank text, invalid director/date/path, web/mobile execution, or backend failure produce no PDF output; and a post-`PUT` output failure keeps the final row committed while reporting a safe partial-success message.
- A failed update is never applied optimistically. `404` clears the stale selection, timeout/connection errors report an ambiguous outcome without retrying, terminal authentication expiry after the centralized recovery policy invalidates the session, and `403` preserves it.
- Ruling deletion sends `DELETE` to the configured bulk endpoint with exactly `{"claves": [...]}` and permits only the centralized one-refresh/one-replay authentication recovery. Keys come from the selected `Dictamen` entities, are deduplicated in stable order, and both the controller and HTTP adapter reject an empty selection.
- Delete is integrated into the paginated search view with multiple selection and an explicit confirmation dialog. Search, update, and delete share the request gate; cancellation, an empty selection, or closing the dialog issues no request.
- A confirmed delete is never applied optimistically. The view clears selection and reconciles through a fresh `GET`; it keeps the current page when valid and falls back to the new last page when deleting the final page. A timeout/connection error remains ambiguous without retry, `404` clears stale selection, and terminal authentication expiry after the centralized recovery policy invalidates the session.
- API payload data and PDF-only context are separate. Director and eligible subjects belong to `PdfRequest`, not `DictamenCreate`.
- Dictamen PDFs without subject rows keep the director signature and role block anchored in the historical lower area; if the ruling text consumes the content page, the complete signature block moves to the lower area of the next institutional page. Subject-table PDFs retain their four-column failed-subject layout, including `Intentos Ordinario` and `Inscrita`.
- Current-period format is five digits ending in `1` or `2`. Eligible failed subjects satisfy `19 <= current - failed < 29` and cannot be deselected.
- When a failed student has no eligible subjects, the ruling form shows the total failed-subject count and an unavailable-ruling explanation without exposing the internal period-rule formula. The create button and handler both block submission in that state.
- Desktop CREATE and UPDATE select and validate a destination before their single API mutation, then use the shared real renderer and local store. CREATE carries eligible subjects; UPDATE builds a PDF request from the final `PUT` response with no subject rows. A cancelled selector or a pre-mutation validation failure issues no API mutation, PDF generation, or save; output failures after mutation never replay or roll back the backend state.
- The interface intentionally uses a light content theme with a dark institutional sidebar. Flet eight-digit hex colors use `#AARRGGBB`; theme regression tests protect semantic text contrast and translucent navigation colors.
- `PdfRequest.fecha_sesion` is PDF-only `date` data. The real renderer and views use the shared `build_session_paragraph()`/`format_session_date()` helpers instead of formatting session dates independently.
